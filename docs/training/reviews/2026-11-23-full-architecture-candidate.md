# 全架構重構候選｜待使用者確認

本提案提供可能的換代設計、遷移合約與驗收。現行可實作範圍是 TD-007-R1 的使用入口和兩條交付路線。候選全架構替換須另行確認。

建議候選採單一交付入口、按任務分配責任、沿用版本化工作包及可讀寫介面。工具按平台能力載入；工作運作、證據與後續決策由同一工作包追蹤。若證據支持替換底層，先建立讀取舊格式和驗證新輸出的介面，逐步替換，保存原資料與可回退版本。

## 八角色及十五技能遷移對照

| 角色 | 技能與移轉 | 應有驗收證據 |
| --- | --- | --- |
| System Lead | project-intake 讀原規格和授權；task-planning 延用工作包 ID 與依賴；resume-project 回讀原狀態、阻礙及操作者 | 舊案例接續，舊工作者拒絕接管 |
| Architect | requirements-spec 保留審閱與來源；architecture-design 保留架構意圖、元件與前置契約 | 已確認規格逐項可追溯且修訂能使下游失效 |
| Developer | implement-feature 沿用原產物驗收；debug-and-repair 保存重現、補丁與對帳 | 同需求在舊新版本輸出等價，故障不會重複寫入 |
| DevOps/SRE | deployment 封裝現有來源、CI、版本／遠端核對與回退 | 模擬未知結果時可查回真實版本和安全動作 |
| QA/UAT | test-and-acceptance 保留獨立測試與回讀 | 原回歸全通過，各層次證據可分別定位 |
| Security | security-review 保留授權、研究資料隔離、存取邊界 | 線上或寫入批准仍由原權責決定，必要拒絕案例全過 |
| Learning Evaluator | learn-from-feedback 維持回饋分類；knowledge-distillation 保存歷史案例與覆核 | 既有案例 ID、來源、用過與未採用的判斷可追溯 |
| Project Manager | project-scope 沿用核准範圍；project-control 沿用進度與停點；delivery-review 沿用成果審查 | 歷史範圍、變更、完成與分層驗收一致 |

## 工作紀錄及測試的相容與回退

1. 固定原 commit、catalog、來源文件及 SQLite 可用備份，逐案收集 task、依賴、revision、decision、事件、artifact、來源與當前操作者。既有 repo 模式保留原路徑及 Git 歷史。用合成副本先比對遷移前後的數目、穩定 ID、引用、授權證據與下一步選擇。
2. 用唯讀舊格式與候選結果對照，哪一項曾批准或已驗就回到原證據。拒絕、失效和未知寫入維持原狀態。切換時指定單一寫入者，經確認才變更讀／寫入口。回退以原提交與已查核備份為基準。
3. 原 CI、SQLite 修訂／競寫、權限拒絕、事故復原及網站驗收全數沿用。增補同案舊新重播、遷移後還原、權限多變、舊工作者仍存活、技術故障與新對話接續。驗收需有原始日誌和精確版本。

## 何時建議全面換代

- 先在相同規格、授權、工具可用性與比較步驟下，至少以兩個不同案例重現必要能力失敗，且證明失敗來自同一工程底層契約。例子包括已完成或撤銷狀態無法正確恢復、無法表達必要且獨立的許可，或版本競寫必然破壞證據。
- 提交模組級修復與相容層的實測結果。只有有界調整不足以解決已重現的問題，且替代版本可在同案消除該失敗，才提出底層換代決策。
- 新架構必須完成資料遷移與回退、具同等或更好的既有功能與拒絕證據，並由使用者確認切換範圍和模式。合成門檻與真平台／真人實測分別取證。
