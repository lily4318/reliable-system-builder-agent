# 全架構重構候選｜乾淨啟用已核准

目前採新版乾淨啟用，實作與驗收見末節。以下保存原候選設計、遷移合約及含既有資料的歷史演練。

建議候選採單一交付入口、按任務分配責任、沿用版本化工作包及可讀寫介面。工具按平台能力載入；工作運作、證據與後續決策由同一工作包追蹤。若證據支持替換底層，先建立讀取舊格式和驗證新輸出的介面，逐步替換，保存原資料與可回退版本。

## 工作紀錄及測試的相容與回退

1. 固定原 commit、catalog、來源文件及 SQLite 可用備份，逐案收集 task、依賴、revision、decision、事件、artifact、來源與當前操作者。既有 repo 模式保留原路徑及 Git 歷史。用合成副本先比對遷移前後的數目、穩定 ID、引用、授權證據與下一步選擇。
2. 用唯讀舊格式與候選結果對照，哪一項曾批准或已驗就回到原證據。拒絕、失效和未知寫入維持原狀態。切換時指定單一寫入者，經確認才變更讀／寫入口。回退以原提交與已查核備份為基準。
3. 原 CI、SQLite 修訂／競寫、權限拒絕、事故復原及網站驗收全數沿用。增補同案舊新重播、遷移後還原、權限多變、舊工作者仍存活、技術故障與新對話接續。驗收需有原始日誌和精確版本。

## 含既有使用中資料的換代考量（原方案）

- 先在相同規格、授權、工具可用性與比較步驟下，至少以兩個不同案例重現必要能力失敗，且證明失敗來自同一工程底層契約。例子包括已完成或撤銷狀態無法正確恢復、無法表達必要且獨立的許可，或版本競寫必然破壞證據。
- 提交模組級修復與相容層的實測結果。只有有界調整不足以解決已重現的問題，且替代版本可在同案消除該失敗，才提出底層換代決策。
- 新架構必須完成資料遷移與回退、具同等或更好的既有功能與拒絕證據，並由使用者確認切換範圍和模式。合成門檻與真平台／真人實測分別取證。

- 本機 Python 3.15 跑新測試 4/4。復現命令 `python -m unittest discover -s tests -p test_workbench_migration_rehearsal.py -v`。GitHub CI 以本次提交的原始日誌為準。

| 檢查 | 實測與等價性 |
| --- | --- |
| SQLite 備份與邏輯匯入 | 使用 SQLite 備份 API 固定時間點，再以 SQL dump 匯入空白 SQLite。11 張表、39 筆資料、schema 與各欄值逐項相同，兩份副本均通過 integrity_check 和 foreign_key_check。比對涵蓋任務／依賴／修訂／操作者、歷史產物及引用、核准與未決決策、PASS／FAIL 驗收與需求修訂回條。相同 context 與下一步，接續仍拒絕非 owner 完成及未核准工作。 |
| 回退切換前的工作台 | 從切換前快照恢復到新路徑，完整表、紀錄與讀取結果等價。原庫逐表核對相同。切換後另取得完整快照留證。 |
| 只複製 SQLite 主檔 | 寫入 WAL 並提交一個決策後，只複製主檔的副本漏掉該決策；SQLite 備份包含。主檔複製不合格。 |
| 遺漏任務／產物綁定 | 其餘表全部逐列相等時，刪掉綁定表會使失效需求被讀成 current。綁定、版本與依賴須一起移轉，核對應用行為。 |
| 外部驗收附件 | 匯入保留 source_ref 與內容列，但副本缺實際附件。另行複製並逐位元檢查可恢復該合成附件。真附件、工作區 ACL、外部帳號或服務授權須各自核驗。 |
| 原操作者與雙寫 | 相同舊 owner 在兩份可寫副本皆可完成同一 RUNNING 任務，並寫出相反驗收。移轉 session 欄位不足以停止舊操作者。切換須實際禁止舊寫入，待對帳後由單一有效位置承接。 |
| 回退後保留新資料 | 回退到舊時間點時，切換後的一筆 PASS 和一筆已解決決策均消失。後切換備份保留兩筆，可供對帳。此輪未執行跨世代合併或用合成決策推定真實授權。 |

**判定:** 同一引擎、同一 schema 的完整快照可保持測得的語意。全面換代仍待決；不同 schema 或儲存引擎尚無等價證據。換代前的待證條件是完整舊新欄位對照、附件與權限清冊、可執行的單一寫入者切換，以及保留切換後寫入的回退方案。未切換任何工作台或外部服務。
