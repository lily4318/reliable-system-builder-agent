# 網站與預約交付

適用 Draft PR #8 的候選操作入口。先查原專案、版本、已確認規格、既有工作紀錄及當前權限。沿用共同規則、資料權責與發布門檻。

| 使用者的話 | 入口 | 交付證據 |
| --- | --- | --- |
| 做網站 | website | 核准需求、設計／施工、表單、桌面與手機版、部署前驗收 |
| 接預約 | booking | 時段與資料收件、通知、管理流程與各服務回讀 |
| 繼續／幫我做 | resume | 上次已驗與受阻事項、接下來可先做的安全工作 |
| 逐步查看 | resume，一步模式 | 每次顯示一項可推進工作，待實測後回報 |
| 修復 | repair | 先取原失敗、受影響範圍、重現與回歸結果 |

自然語言由 Agent 解析，命令列接受表內字詞或英文入口 ID。在有授權的私人工作台，用已確認工作包中的 `website-`、`booking-` 或 `repair-` 任務 ID 明示分流。舊任務仍可走 resume。現有專案若只有原 repo，從原規格、版本及進度檔採用同一分流原則。

```text
python -m src.delivery_routes website --workspace <已授權工作區> --answers <現有答案.json>
python -m src.delivery_routes booking --workspace <已授權工作區>
python -m src.delivery_routes resume --workspace <已授權工作區> --stepwise
```

命令唯讀回傳可先做的任務、當前需確認的事項及建議技能。施工仍使用工作台原 start／finish、權限驗證、相依與版本。新站無既有工作包時，入口以原訪談規格預填，只列未答欄位並保留整份規格審閱。接續時先讀既有 scope、已交付成品和狀態，驗證之後才選下個步驟。

## 網站路線

1. 以原訪談及規格審閱處理未確認的需要。已確認欄位從原來源預填，重大變更才重開確認。
2. 需求、素材來源、頁面與手機體驗交 architecture-design 和 implement-feature。必需表單使用可測驗收資料。若預約服務未備妥，保留相容的預約入口，將相關阻礙記入原工作包。
3. 由 test-and-acceptance 實核桌面與手機、鍵盤與表單、錯誤與空狀態，再保存精確版本及結果。現階段可交候選成果和部署準備，任何外部操作須具獨立授權。

## 預約路線

1. 核對可用時段、名額、取消／重複規則、最少必要資料、各角色可訪問範圍及現有網站整合點。在本機樣本先核准測試工作包。
2. 依核准範圍串接處理、資料表及通知的各層契約。只有當前步驟確需本人登入、授權或決策才交接，給當步服務入口、按鈕或欄位、預期畫面與錯誤接續。其餘能安全施工的工作繼續。
3. 用同一測試代碼核表單、處理結果、原始紀錄與對應通知。驗重複送出、名額不足、通知失敗、唯讀對帳、同鍵復原及隔輪接續。發布、正式收件及真人驗收各自核對。

## 這輪可重現案例

```text
python -m unittest discover -s tests -p test_academic_booking_delivery.py -v
```

案例使用可呼叫的本機 WSGI 表單、既有 SQLite 名額／請求對帳及獨立的本機通知回條。故障時保留已提交的預約，先查回條，再以同一測試代碼完成通知。工作區新程序透過命令列讀回當前阻塞及已完成資料。GAS、Sheets、LINE 皆為本機合成證據，真瀏覽器版面、外部服務與新聊天須另行驗收。樣本通知儲存採唯一鍵，實際通知供應商須另核同鍵及投遞確認機制。
